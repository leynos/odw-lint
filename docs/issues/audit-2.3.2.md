# Post-step audit after roadmap task 2.3.2

- Status: Proposed findings
- Scope: `origin/main` at commit `0fc256c` inspected from the
  `df12-audit-2.3.2` git-donkey worktree
- Trigger: audit run after the dual-compatibility parity fixtures landed on
  `origin/main` (roadmap task 2.3.2)

This audit was run after the dual-compat parity fixtures, manifest, and
`dual-compat-parity.test.ts` suite landed on `origin/main`. It used `grepai`
for canonical main-branch intent search, `leta`/exact text search for

## Finding 1: Dual-compat manifest is excluded from `make refresh-fixtures`

- Category: inconsistency
- Severity: Medium
- Location: `tests/static-analysis/fixtures/refresh-metadata.ts`
  (`MANIFEST_PATHS`, `FixtureRefreshCounts`) versus
  `tests/static-analysis/fixtures/dual-compat.ts`

Every other committed fixture corpus (`odw-examples`, `masking`, and the five
`invalid-workflows` manifests) is regenerated by `refreshFixtureMetadata`,
whose `MANIFEST_PATHS` list and `FixtureRefreshCounts` shape drive `make
refresh-fixtures`. The new dual-compat manifest is absent from both. As a
result the SHA-256 digests and UTF-8 span offsets in `dual-compat.ts` (for
example `start.offset: 235` for `date-now.js`) must be transcribed and updated
by hand, while the freshness test only *detects* drift rather than repairing
it. This contradicts the project convention, stated in the developers' guide,
that fixture hashes, spans, and `spanText` should "remain derived from source
text rather than hand-edited".

Proposed fix: either add the dual-compat manifest to the refresh contract
(extend `MANIFEST_PATHS`, add a `dualCompat` count to `FixtureRefreshCounts`,
and teach `refresh-writers` to project the pure-metadata and deterministic-time
families), or, if hand-maintenance is a deliberate scoping decision for 2.3.2,
record that exception explicitly (see Finding 2). The former is preferred
because it keeps a single derivation path for all corpora.

## Finding 2: Refresh-fixtures documentation no longer matches reality

- Category: docs-gap
- Severity: Medium
- Location: `docs/developers-guide.md` around lines 318-322 and 501-503

The guide instructs maintainers to "Run `make refresh-fixtures` after changing
workflow fixture source, copied ODW examples, or static-analysis fixture
manifests" and states that fixture metadata should stay "derived from source
text rather than hand-edited". Neither statement holds for the dual-compat
manifest, which the refresh tool does not manage. A maintainer editing a
dual-compat fixture and running the target will see the file reported as
out-of-scope and silently left stale, then be forced to hand-edit the
manifest, exactly the anti-pattern the surrounding prose warns against.

Proposed fix: add an explicit note to the dual-compat paragraph stating that
its manifest is currently maintained by hand and is not refreshed by `make
refresh-fixtures`, and cross-reference the freshness guard in
`dual-compat-parity.test.ts` that catches drift. Remove the note once Finding 1
folds dual-compat into the refresh contract.

## Finding 3: Documentation-path (`docs`) parity is derived but never asserted

- Category: test-gap
- Severity: Medium
- Location: `tests/static-analysis/dual-compat-parity.test.ts`
  (`ComparableDiagnostic`, `comparableLiveDiagnostics`,
  `comparableFixtureDiagnostics`)

Both sides of the parity comparison compute a repository-relative documentation
path: the manifest via `diagnostic()` -> `ruleDocsPath(ruleDefinition)` in
`manifest-types.ts`, and the live pipeline via `createRuleDiagnostic` ->
`ruleDocsPath` in `src/diagnostics/rule-diagnostic.ts` (the live `Diagnostic`
type carries an optional `docs` field, `src/diagnostics/types.ts:64`). However,
`ComparableDiagnostic` omits `docs`, so the dual-compat suite never checks that
the live diagnostic's documentation path matches the manifest. The
invalid-workflow fixtures do verify documentation-path parity, so this is a
weaker, inconsistent contract for the deterministic-time warnings - and the
manifest's derived `docs` value is effectively dead metadata in the comparison.

Proposed fix: add `docs` to `ComparableDiagnostic` and include it in both
`comparableLiveDiagnostics` and `comparableFixtureDiagnostics`, so the
documentation-path contract is asserted for deterministic-time diagnostics on a
par with the invalid-workflow corpus.

## Finding 4: Test title references a non-existent `scanDualCompat` symbol

- Category: inconsistency
- Severity: Low
- Location: `tests/static-analysis/dual-compat-parity.test.ts:111`

The test case is titled "matches scanDualCompat warning diagnostics and spans",
but no `scanDualCompat` function exists anywhere in `src` or `tests`; the suite
drives the public `lintWorkflowSource` pipeline. The `scanDualCompat` reference
was removed from `docs/developers-guide.md` when task 2.3.2 landed, leaving the
test title as the sole stale mention. A reader searching for `scanDualCompat`
will find only this misleading label.

Proposed fix: rename the test case to describe the actual behaviour, for
example "matches deterministic-time warning diagnostics and spans", so the
title tracks the real pipeline entry point.

## Finding 5: `findDualCompatFixture` is exported but unused

- Category: separation-of-concerns
- Severity: Low
- Location: `tests/static-analysis/fixtures/dual-compat/corpus.ts:34`

`findDualCompatFixture` is defined, documented, and exported, but no test or
source module imports it (verified by exact-text search across `tests` and
`src`). Its sibling `findInvalidWorkflowFixture` is used in four suites, so this
appears to be speculative scaffolding copied from the invalid-workflow corpus.
Unused exported helpers dilute the public test-support surface and invite drift.

Proposed fix: remove `findDualCompatFixture` until a consumer needs it, or fold
it into the shared helper proposed in Finding 6 so a single lookup exists.

## Finding 6: Corpus lookup and location scaffolding is duplicated

- Category: similarity
- Severity: Low
- Location: `tests/static-analysis/fixtures/dual-compat/corpus.ts` versus
  `tests/static-analysis/fixtures/invalid-workflows/corpus.ts`

`findDualCompatFixture` and `findInvalidWorkflowFixture` are near-identical:
both take a `{ family, fileName }` query, run the same `Array.find` predicate
over their snapshot array, and throw a `Missing ... fixture` error. The
`FixtureCorpusLocation` objects differ only in `manifestRoot`. This is the same
manifest/corpus/freshness/parity scaffolding now repeated across the
dual-compat, invalid-workflows, odw-examples, and masking corpora. Roadmap task
2.3.5 ("Consolidate fixture corpus and parity projection ownership") already
targets this area, so the duplication is known but has grown with 2.3.2.

Proposed fix: extract a generic `findFixtureSnapshot(snapshots, query, label)`
and a shared corpus-location builder, then have each corpus module delegate.
Track this under roadmap 2.3.5 rather than as a standalone change.

## Finding 7: Deterministic-time parity asserts rule classes two ways

- Category: complexity
- Severity: Low
- Location: `tests/static-analysis/dual-compat-parity.test.ts`
  (deterministic-time block versus `expectedRuleClasses` /
  harness-integration block)

The deterministic-time block asserts `outcome.ruleClasses` equals
`expectedDiagnostics.map((diagnostic) => diagnostic.rule)` - a raw, non-unique,
source-ordered projection - whereas `outcome.ruleClasses` is produced by
`loaderParityOutcome` as a *unique, sorted* set, and the harness-integration
block correctly compares against the unique-sorted `expectedRuleClasses()`
helper. The two assertions agree today only because every dual-compat fixture
carries exactly one diagnostic. A future fixture with two diagnostics, or two
rules in non-alphabetical order, would make the deterministic-time assertion
compare a sorted-unique list against a raw list and fail, or pass by accident,
even though behaviour is correct.

Proposed fix: use the `expectedRuleClasses()` helper (or compare the full
`comparableLiveDiagnostics` sequence) in the deterministic-time block so a
single, order-safe derivation of expected rule classes is used throughout.

## Finding 8: Dual-compat manifest entries are deep-frozen redundantly

- Category: duplication
- Severity: Low
- Location: `tests/static-analysis/fixtures/dual-compat.ts` (array-level
  `deepFreezeFixtureManifest`) versus `manifest-types.ts` (`dualCompatFixture`
  and `diagnostic` each call `deepFreezeFixtureManifest`)

Each manifest entry is frozen inside `dualCompatFixture`, each diagnostic and
span inside `diagnostic`, and then the whole array is passed through
`deepFreezeFixtureManifest` again in `dual-compat.ts`. The re-freeze is a
harmless no-op on already-frozen objects, but the layered calls obscure where
the immutability boundary actually lives and diverge in style from a
freeze-once-at-the-boundary approach.

Proposed fix: freeze once at the manifest boundary (or add a short comment
explaining the intentional layered freezing) so the immutability contract has a
single obvious owner.
